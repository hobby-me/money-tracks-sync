# synk — модель доступа и безопасность

Сервер хранит финансовые данные, поэтому здесь описано, кто что может,
где проходит граница между приложением и сервером, и что защищает данные
на хосте. Меняешь правило — правь этот файл в том же коммите.

## Роли

| Кто | Что может |
|---|---|
| **Оператор** (ssh на сервер, `synk`/`synk-tui`) | Заводить и удалять учётки, выпускать любые коды (в любую учётку, обычные и админские), отзывать устройства, снимать админство, смотреть статистику. |
| **Админ-устройство** учётки | Всё, что обычное устройство, плюс выпускать коды подключения **в свою** учётку. Коды из приложения всегда создают обычное устройство. |
| **Обычное устройство** | Синхронизировать данные своей учётки: push, pull, checksum, snapshot, фото. Приглашать не может. |

Админство привязано к устройству, не к человеку. Первое устройство учётки
становится админом через `synk account add --bootstrap`; следующие — только
кодом с сервера: `synk invite --account <id|имя> --admin`. Отозванное
устройство теряет доступ немедленно (проверка `revoked_at` на каждом
запросе), админство снимается `synk device demote`.

## Как это выглядит для семьи

1. Оператор заводит учётку и печатает админ-код: `synk account add --name Family --bootstrap`.
2. Твой телефон вводит код → он админ учётки.
3. Телефон жены подключаешь из приложения на своём телефоне
   («Подключить устройство» → код на 10 минут). Её телефон обычный.
4. Ей нужен планшет: код выдаёт твой телефон. Либо один раз выдаёшь ей
   админ-код с сервера, и дальше она приглашает сама.
5. Телефон потерян: `synk device revoke --id <ID>` (или `x` в TUI).
   Устройства, которые он успел пригласить, видны в `synk device list` по
   дате создания; при сомнениях отзывай и их.

## Что намеренно недоступно по HTTP

- **Заведение учёток** (`POST /v1/accounts` удалён). Иначе токен на
  телефоне становился глобальным ключом.
- **Код в чужую учётку** (`POST /v1/invites?account=…` отвечает 403 даже
  админу). Кросс-учёточные операции — только с сервера.
- **Приглашение с обычного устройства** (`POST /v1/invites` требует
  админский токен, иначе 403). Украденный обычный телефон не может
  завести злоумышленнику постоянный доступ.

Если последнее правило окажется неудобным, оно меняется одним словом в
`internal/server/server.go`: `auth(true, s.handleInvite)` → `auth(false, …)`.
Цена — любой украденный телефон учётки сможет пригласить чужое
устройство, и отзыв украденного не отзовёт приглашённых.

Приложение узнаёт свою роль из ответа `POST /v1/register`: поле
`is_admin`. На обычном устройстве кнопку приглашения стоит скрывать или
подписывать «код выдаёт устройство-администратор».

## Токены и коды

- Токен устройства: 256 бит случайности, выдаётся один раз при
  регистрации, в базе только SHA-256. Не истекает; отзыв — `device revoke`.
- Код приглашения: 80 бит (16 знаков base32 Крокфорда), одноразовый,
  живёт 10 минут, в базе только хэш. `POST /v1/register` ограничен
  10 попытками в минуту с одного IP.
- Все отказы (401, 403, 429, 507, неверный код) пишутся в журнал с IP,
  методом и маршрутом: `journalctl -u synk | grep deny`. Сам токен в
  журнал не попадает.

## Пределы

| Что | Предел | Ответ |
|---|---|---|
| Пачка правок | 500 правок, 8 МБ тела | 400 |
| Поля правки | `op_id`, `entity`, `entity_uuid`, `device_id` ≤ 64, `hlc` ≤ 32 | 400 |
| Фото | 20 МБ, имя `[A-Za-z0-9_-]{1,64}.(jpg|jpeg|png|webp)` | 413 / 400 |
| Учётка целиком (sync.db + фото) | своя квота учётки, иначе глобальная `SYNK_ACCOUNT_QUOTA_MB` (1 ГБ); 0 — без лимита | 507 |

Квота считается по диску перед push и перед сохранением фото; она
защищает хост, где рядом живут другие сервисы, от одного разбушевавшегося
или украденного устройства.

- **Глобальная** — `SYNK_ACCOUNT_QUOTA_MB` в `/opt/synk/synk.env`
  (плейбук, рестарт сервиса). Действует для учёток без своей.
- **Своя** — `synk account add --quota-mb N`, `synk account quota
  --account <id|имя> --mb N` (0 — без лимита, `--default` — вернуть на
  глобальную), в TUI клавиша `Q` или `:quota <учётка> <МБ|0|default>`.
  В таблицах своя квота помечена `*`.
- **Прозрачность для клиента** — `GET /v1/quota` отдаёт
  `{"quota_bytes": N, "used_bytes": M}` (0 — без лимита); ответ 507 несёт
  те же два поля, чтобы приложение показало «занято M из N», а не голую
  ошибку.

## Изоляция данных

- Одна SQLite на учётку: `acc/<account_id>/sync.db`, фото рядом. Токен
  скоупит обработчик на файл своей учётки, чужие данные недостижимы по
  построению; тест `TestAccountIsolationOverHTTP` это фиксирует.
- Сервер payload не читает и не интерпретирует (даже в checksum он не
  входит). Это позволяет включить E2E-шифрование на клиенте без изменений
  сервера; в дизайне cash-tracks оно помечено как отложенное.

## Хост

- Данные `0600`, папки `0700`, владелец `synk` (`UMask=0077` в юните,
  плейбук разово подтягивает права существующих файлов).
- systemd-юнит: `ProtectSystem=strict`, запись только в `/opt/synk/data`,
  без capabilities, фильтр syscall'ов, сеть только localhost
  (`IPAddressAllow=localhost`). `systemd-analyze security synk` — 1.1 OK.
- API слушает `127.0.0.1:8090`, метрики `127.0.0.1:8091`; снаружи
  только nginx на 443 (TLS 1.2+/1.3, HSTS на сутки) и ssh.
- ssh: только по ключу (`PasswordAuthentication no`,
  `PermitRootLogin prohibit-password` в `/etc/ssh/sshd_config.d/00-hardening.conf`,
  номер 00 — чтобы cloud-init с `PasswordAuthentication yes` не победил),
  fail2ban, ufw.
- Диск **не** шифруется, бэкапов нет. Кто получает root на хосте — читает
  всё. Ответ на это — E2E на клиенте и/или LUKS, оба вне этого репозитория.

## Проверка после деплоя

```bash
curl -s -o /dev/null -w '%{http_code}\n' -X POST https://sync.example.com/v1/accounts   # 404
curl -s -o /dev/null -w '%{http_code}\n' https://sync.example.com/v1/checksum -H 'Authorization: Bearer x'   # 401
curl -sI https://sync.example.com/healthz | grep -i strict-transport   # HSTS
ssh vds-app-01 'systemd-analyze security synk | tail -1; journalctl -u synk --since "1 hour ago" | grep deny | tail'
```
